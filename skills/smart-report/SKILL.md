# 智能报告生成（SmartReportGen）

依赖 MCP 服务 `smartreportgen`（Streamable HTTP，默认 `http://localhost:18601/mcp`）。
若工具不可用，提示用户先部署服务并为所用 agent 注册 MCP（见部署文档 `docs/DEPLOYMENT.md`「接入 Agent」），不要凭空编造数据。

本技能与 agent 无关（Claude Code、Codex、Cursor 等均可使用）。没有技能机制的 agent 可调用 MCP 工具 `get_skill_guide` 获取本文全文。

**认证与权限**：MCP 必须携带代表员工本人的令牌——员工用海尔 IAM 登录管理台后在「我的令牌」自助签发，或直接使用 IAM access token（服务端向 IAM 核实工号）。工号决定能检索哪些业务场景、能访问哪些数据表：
- 检索、取表、探查、查询、校验、渲染都只覆盖**已授权**的场景与表；任何 SQL（含 JOIN / 子查询）引用未授权表都会被拒绝。
- 收到 `error_type: permission_denied` 时**不要改写 SQL 绕过**，直接告诉用户缺少哪张表/哪个场景的权限、应向管理员申请；可在已授权范围内给出降级方案（例如去掉依赖该表的章节）。
- 401 / 令牌无效或过期：提示用户用 IAM 登录管理台，在「我的令牌」重新签发，并更新 agent 的 `SMARTREPORT_TOKEN`（通常需要重开 agent 会话）。可先调用 `whoami` 查看当前身份与权限。
- 模板与报告按创建人隔离：只能读取、修改、渲染本人创建的模板。

产出物：一份存储在报告库中的**报告模板（markdown）**和由它生成的**HTML 报告**（含全局筛选联动）。
最终回复给出报告链接、核心结论摘要和需要用户确认的口径假设。

## 流程总览

| 步骤 | 目的 | MCP 工具 |
|---|---|---|
| a | 解析需求 → 在有权限的场景中混合检索 → 拿到有权限的数据表 | `whoami`（可选）→ `search_business_scenarios` → `get_dataset_tables` |
| b | 探查数据 → 确定分析目标 → 设计章节/结论/图表/布局 | `describe_table`、`run_query`、`get_template_spec` |
| c | 设计全局筛选与联动 | （写入模板 front matter） |
| d | 检索通用规则（设计令牌）+ 场景私有规则 → 按规则设计结构、健康度与升降色 | `get_style_rules` |
| e | 校验并存储模板 → 生成 HTML | `validate_report_template` → `save_report_template` → `render_report_html` |
| f | 存储 HTML（render 已自动存储；若对 HTML 做了改写用 save_report） | `save_report` / `get_report` |

## a. 解析需求，锁定业务场景

1. 先从用户需求中提炼：**分析对象、时间范围、关注维度、关注指标、对比方式（同比/环比/目标）、受众**。缺失项不必追问，采用合理默认并在最终回复中说明。
2. 调用 `search_business_scenarios(query=用户原话, top_k=3)`。
   - 取第 1 名；若返回 `tip` 提示相关度接近或偏低，阅读各候选的 business_description 判断，仍无法确定时**向用户确认**再继续。
   - 无命中：可能是业务术语不同，也可能是**没有该场景权限**（检索只覆盖已授权场景）。换术语重试一次，仍无则告知用户并停止。
3. 调用 `get_dataset_tables(dataset_id)` 获取该场景中**你有权限的**数据表与数据源类型（决定 SQL 方言：postgresql / mysql / starrocks / oracle / api=DuckDB）。
   若返回 `unauthorized_table_count > 0`，说明还有表无权访问：只用已授权的表设计报告，并在最终回复中说明哪些分析因权限受限未覆盖。

## b. 探查数据，确定分析目标与报告结构

**先探查，后设计；结论必须来自查询结果，禁止编造数字。**

1. 对每张相关表调用 `describe_table`：识别
   - 维度：低基数文本（大区、渠道、品类…）、日期（看 `full_min/full_max` 确定真实时间范围）；
   - 度量：数值列（金额、数量、成本…）；
   - 关联键与表之间的粒度（明细 / 日 / 月、目标表粒度）。
2. 用 `get_template_spec` 阅读模板语法（每个会话至少读一次）。
3. **确定分析目标**：一句话写清“要回答的问题”（如“今年增长从哪来、毛利为何下滑”），写入 `analysis_goal`。
4. 用 `run_query` 计算支撑结论的关键事实（总量与同比、各维度排名与增速、结构占比变化、异常点）。每个维度先算一遍，**只为有信号的维度建章节**——差异微小的维度合并或舍弃，不凑数。
5. 设计报告结构（按维度视角平铺）：
   - 第 1 节固定为“经营概览/总体概览”：KPI 行 + 时间趋势 + 目标达成（若有目标数据）。
   - 后续每节一个维度视角：时间、区域、渠道、品类/商品、客户、组织……标题即该维度的核心发现（如“区域维度：西南高增长，华北负增长”）。
   - 每节开头用 `>` 写**本节汇总结论**：量化、有对比、有归因；关键数字尽量用 `{{度量}}` 实时指标，静态数字注明“默认口径”。
   - 每节下 1–3 个 `###` **子结论**，每个子结论配 **2–4 个**图表说明“这个结论是怎么得出来的”，每个图表写 `note`。
   - 最后一节“结论与行动建议”：总结 + 3–5 条可执行建议（对应前文发现）。
6. 设计查询（front matter `queries`）：
   - 尽量**一个主查询**聚合到“图表 + 筛选”所需的最细粒度（例：月×大区×省份×渠道×品类×商品），行数控制在 1 万以内；粒度不同的数据（如只到大区的目标）单独一个查询。
   - 同比：在 SQL 中准备 `xxx_ly` 去年同期列（FULL OUTER JOIN 同键），度量用 `sum(x)/sum(x_ly)-1`。
   - 比率一律写成聚合之比（`sum(profit)/sum(amount)`），保证任意筛选组合下口径正确。
7. 选图与布局：

| 要表达 | 首选图表 | 宽度建议（span/12） |
|---|---|---|
| 核心指标 | `kpi`（≤4 个一行；5 个自动 3+2；`sub` 带同比并声明 trend 方向） | 自动 |
| 时间趋势 / 今年 vs 去年 | `line`、`combo`（柱=今年，线=去年/增速） | 8–12 |
| 排名（类别多或标签长） | `hbar` + `top` | 6 |
| 分类对比 / 增速对比 | `bar` | 4–6 |
| 构成占比（≤6 类） | `donut` | 4–5 |
| 构成随时间变化 | `stacked_bar` / `stacked_area` | 8 |
| 两维交叉 / 持续性 | `heatmap` | 12 |
| 两指标关系 / 象限 | `scatter`（气泡=规模） | 6–7 |
| 达成率 | `gauge`（整体）/ `bullet`（实际 vs 目标，可按类目多行） | 4 / 6–8 |
| 明细 / 下钻 | `table`（`bar_in_cell`） | 12 |

   布局原则：同一行宽度合计 12；主图宽、辅图窄（8+4、7+5）；同一行图表类型的“视觉重量”接近；类别多的 `hbar` 增加 `height`（约 28px/类）；不确定时**省略 span 让渲染器自动排布**。

## c. 全局筛选与联动

- 一般 3–6 个筛选器，按“时间 → 组织/地域（上级→下级）→ 业务维度”排序，下级自动级联上级（如 大区 → 省份）。
- 时间离散值用 `range`（月份/年份），连续日期用 `date_range`；可 `default: "last:12"`。
- 字段名在不同查询中不一致时用 `targets` 映射；不应受影响的查询（如目标表遇到渠道筛选）列名本就不存在即自动不受影响，或用 `exclude`。在相关图表 `note` 中说明口径。
- `presets` 设计 3–5 个常用业务场景（季度、重点渠道、重点区域）一键切换。
- 让排名/构成图的 `x` 与某个 select/multi 筛选器同字段，即可**点击图表联动筛选**全报告。

## d. 样式设计

1. 调用 `get_style_rules(business_scenario, query=用户需求)`，逐条阅读每条规则的 `items`（类别：版式结构 / 图表选择 / 必备筛选 / 好坏判定 / 涨跌颜色 / 数字格式 / 文案要求）。
   返回的是管理员配置的通用规则 + **当前用户本人**为该场景配置的样式（只作用于本人的报告）。
   **优先级：业务场景规则 ≥ 通用规则 ≥ 内置默认**——两者冲突时以业务场景规则为准（`precedence` 字段同此说明；`overridden_by` 标明哪些视觉令牌被哪条规则改过）。
2. 渲染时会自动把通用规则 + 场景规则的设计令牌应用到报告，**模板不需要、也不应该复制整套 theme**。只在以下情况写 `theme` 覆盖：用户明确确认过的升降色（如“红涨绿跌”）、规则允许的页面选项（`header_style` 等）。
3. 把规则落实到模板结构：
   - **健康度**：只有能明确判好坏的指标卡 / 仪表盘 / 子弹图才写 `status`（口径优先取场景规则，如“达成率 ≥100% 向好、≥95% 关注”）；判不了好坏的卡不写，保持蓝色。
   - **升降色**：KPI 的同比/环比 sub 必须声明方向——`trend: up`（越大越好）、`trend: down`（越小越好，如成本、投诉率、时长）、`trend: none`（无方向，不着色）。
   - **单位**：金额度量写 `unit: 元` 并用 `format: wan`，主值显示“万元”后缀，图表卡标题右侧自动出现单位标签。
   - 不在图表中写死颜色（`color`），多系列靠分类色板顺序取色，正负柱自动用发散色阶。

## e. 校验、存储与生成

1. `validate_report_template(markdown, dataset_id)`：修复全部 `errors`；认真处理 `warnings`（缺汇总结论、结论无图表、数据量过大等）；检查返回的行数与筛选取值是否符合预期。循环直到 `ok: true`。
2. 核对结论文本中的每个静态数字都能在 `run_query` 结果中找到出处；与实时指标冲突时以实时指标为准改写文本。
3. `save_report_template(name, markdown, dataset_id, user_requirement, analysis_goal)` → 得到 `template_id`（修改已有模板时传 `template_id`，版本号自动递增）。
4. `render_report_html(template_id)` → 生成 HTML 并**自动存入报告库**，返回 `report_id` 与带查看凭证的 `url`（默认 7 天内免登录可看）。

## f. 存储 HTML

- `render_report_html` 已完成存储。仅当需要对生成的 HTML 做额外改写时：`get_report(report_id, include_html=true)` → 修改 → `save_report(name, html, template_id)`。优先修改模板再重新渲染，而不是直接改 HTML。

## 最终回复格式

```
已生成报告：<标题>
- 报告链接：<url>（离线单文件：<url>/download）
- 模板：#<template_id> v<version>，业务场景：<场景>
- 核心结论：3–5 条，每条带关键数字
- 口径与假设：时间范围、同比口径、未覆盖的维度/数据缺口
- 权限说明（如有）：因无权访问而未纳入的表/分析
```
